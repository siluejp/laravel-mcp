# FastMCPベース コーディング支援MCPサーバー憲章

## 基本原則

### I. Python第一の開発
MCPサーバーとそのコンポーネントは、すべてモダンで慣用的なPythonで開発されなければなりません (MUST)。

### II. FastMCPフレームワークの採用
プロジェクトは、サーバーとクライアントの実装を含め、Model Context Protocolを処理するコアとしてFastMCPフレームワークを使用しなければなりません (MUST)。

### III. シンプルさと速度の重視
FastMCPの哲学に従い、プロジェクトはシンプルでクリーンなコードと高いパフォーマンスを優先すべきです (SHOULD)。不要な複雑さは避けるべきです。

### IV. ツールとデータの統合
主な目標は、LLMを様々なツールやデータソースに接続することです。新しい統合は、モジュール式で再利用可能なコンポーネントとして設計されなければなりません (MUST)。

### V. 本番環境への対応
サーバーは、FastMCPの組み込みツールを活用し、本番環境へのデプロイ、認証、スケーラビリティを念頭に置いて構築されなければなりません (MUST)。

## 開発ワークフロー

### 仕様駆動
すべての新機能や大幅な変更は、ユーザーストーリー、要件、成功基準を概説した仕様書（`spec.md`）から始めなければなりません(MUST)。これにより、実装前の明確さと整合性が確保されます。

### 計画とタスク
仕様が承認されたら、技術計画（`plan.md`）と詳細なタスクの内訳（`tasks.md`）を作成しなければなりません(MUST)。これにより、実装のための明確なロードマップが提供され、進捗の追跡が容易になります。

## ガバナンス

### 改正プロセス
この憲章の改正には、文書化された提案とレビューが必要です。提案では、変更点、その根拠、および既存の原則やワークフローへの影響を概説しなければなりません。

### バージョン管理
この憲章への変更は、セマンティックバージョニング（MAJOR.MINOR.PATCH）に従います：
- **MAJOR**: 中核となる原則の削除など、後方互換性のない変更。
- **MINOR**: 新しい原則の追加や、互換性のある大幅な変更。
- **PATCH**: 軽微な明確化、誤字の修正、または実質的でない変更。
